# Owner correction — hard humanization delivery admission

Date: 2026-09-20
Status: **DIRECT OWNER CORRECTION / BLOCKING DELIVERY CONTRACT**

Joel's current rule:

> you should not be showing me something that doesn't pass all of your reviews. it should also pass pangram at that point after your reviews. if not then you either keep working or tell me if you need help understanding how to fix it, and if you need help you need to show me exactly the map you used to write each sentence.

## Hard owner-facing delivery rule

A generated humanization candidate may be shown to Joel as a candidate only after it has passed **all applicable internal reviews** and then passed the required Pangram checks.

The owner is not an ordinary intermediate QA surface.

If a candidate fails an internal review or Pangram:
- do not present it to Joel as a candidate;
- continue working autonomously;
- if the failure shows the current method is saturated, switch methods automatically;
- interrupt Joel only when a real authorial/semantic uncertainty blocks further repair.

If owner help is genuinely required, do not merely say the prose failed. Show the exact contemporaneous construction map that generated **each affected sentence**.

## Required admission sequence

### 0. Meaning/source freeze
Before generation:
- freeze exact changed scope;
- freeze owner locks/source units and provenance;
- freeze authorized semantic delta;
- identify the section/natural-boundary mesoscale role.

The preservation ledger exists here for custody, not as a prose outline.

### 1. Generate without critic-scorecard exposure
The writer may receive:
- live thought / source material;
- mesoscale paragraph/section role;
- only the minimum relevant literal positive calibration examples.

The writer must **not** compose from:
- the preservation-unit list in source order;
- AI-tell scorecards;
- Human-tell checklists;
- sentence-by-sentence pass/fail targets.

### 2. Plain-reader comprehension gate — blocking
Read the literal prose in publication order with the ledgers out of view.

Require:
- every sentence is understandable on first read;
- no reader must reconstruct hidden preservation logic;
- referents are clear;
- chronology and causality are clear;
- sentence syntax does not overload working memory;
- the paragraph makes the original distinction easier, not harder, to understand;
- the next sentence follows naturally from the reader's live question.

Any failure blocks advancement.

### 3. Semantic/reality/fidelity gate — blocking
Check:
- exact meaning;
- actor/action/object;
- causality/chronology;
- certainty;
- source attribution/provenance;
- no invented memory, event, diagnosis, mechanism, treatment, threshold, or authorial stance;
- zero unexplained substantive deltas.

### 4. Mesoscale architecture gate — blocking
Check:
- section map;
- paragraph roles and unequal thought duration;
- heading fit;
- curious-reader chain;
- true stopping point;
- no local repair has inverted the map hierarchy.

### 5. Humanization-shape review — blocking
Only now inspect:
- predictable marching advancement;
- semantic-ledger visibility;
- local closure/aftercare;
- symmetric branching;
- instructional staircase;
- synthetic voice;
- other active owner-calibrated AI-shaped failure modes.

Human-facing tell catalogs are diagnostic/retrieval aids here, not writer requirements.

### 6. Second cold read — blocking
After the AI-shape review, reread the literal prose as prose again.

Do not allow a stylistic repair to make the passage less understandable.

If this review changes the text, restart from step 2.

### 7. Preservation re-proof — blocking
After the literal final candidate is frozen:
- forward traceability;
- reverse traceability;
- zero unexplained substantive deltas.

Any substantive edit invalidates this proof.

### 8. Pangram — blocking before owner candidate delivery
Pangram happens **after** all internal reviews pass.

Required detector boundary:
- each materially model-written paragraph independently where technically meaningful;
- the complete model-written natural boundary;
- the complete section only as secondary context when owner-authored Human prose is present.

Do not use Joel's known-Human paragraph to mask a red model paragraph.
Do not pad short paragraphs to manufacture detector validity.

The candidate is owner-delivery eligible only when the applicable model-written boundaries pass the current Pangram acceptance target.

If Pangram fails:
- do not show the candidate;
- record the exact result and localization;
- continue repair when a useful gradient exists;
- switch architecture when repeated failure is flat/saturated.

## Review invalidation rule

**Any substantive prose change invalidates all reviews at and after the earliest affected gate.**

Examples:
- readability edit -> restart comprehension and every later gate;
- semantic edit -> restart semantic/fidelity and every later gate;
- architecture edit -> restart architecture, shape, cold read, preservation, Pangram;
- detector-driven wording edit -> restart plain-reader comprehension, semantic/fidelity, architecture, shape, preservation, and Pangram.

A previous candidate's PASS never transfers automatically to revised bytes.

This directly prevents the H -> H2 failure, where a post-ledger optimization created unreadable prose without restarting the entire admission chain.

## No internal-score optimization

Do not rewrite prose merely to improve:
- number of Human tells;
- number of AI tells;
- sentence-job distribution;
- paragraph asymmetry;
- preservation-unit packing;
- a ledger score.

Those are diagnostic observations.

A repair must have a reader-facing causal reason:
- clearer;
- more natural thought movement;
- removes an actual closure/symmetry/staircase defect;
- restores source-grounded cognition;
- fixes fidelity;
- responds to useful Pangram localization without harming the above.

## Owner-help escalation packet

If Chat genuinely cannot determine how to fix a failed passage, Joel must receive the actual generation trace rather than a vague request for help.

For **each affected sentence**, show:

1. **Exact sentence**
2. **Exact source meaning/unit(s) it was meant to carry**
3. **Mesoscale node / paragraph role**
4. **Exact local map used while composing it**
   - e.g. `notice -> reaction -> recurrence -> unresolved complication`
5. **Literal donor/map source used, if any, with provenance**
6. **Any generative operation actually active**
   - chronology;
   - subordination;
   - recurrence;
   - direct counsel;
   - metaphor;
   - etc.
7. **Why that sentence was placed there**
8. **What the next sentence was supposed to do**
9. **Which review failed and exactly why**
10. **Pangram result/localization if already measured**

This map must be the **contemporaneous map actually used to write the sentence**, not a post-hoc reconstruction invented after failure.

Therefore generation must preserve an internal construction trace while writing, even though that trace is hidden from ordinary owner delivery.

## Help boundary

Ask Joel for help only when:
- a real authorial judgment is absent;
- source provenance is uncertain;
- two materially different meanings remain possible;
- repeated architecture changes fail and the missing distinction appears to be owner cognition rather than an engineering issue.

Do not ask Joel merely because:
- Pangram is red;
- the prose is model-shaped;
- an implementation strategy failed;
- a better technical next experiment is available.

## Stop/admission state

Normal loop:
`generate -> comprehend -> fidelity -> architecture -> AI-shape review -> cold read -> preservation -> Pangram -> deliver only if all PASS`

Failure loop:
`FAIL -> repair -> invalidate downstream gates -> restart -> Pangram -> ...`

Saturation:
`repeated same structural failure -> change architecture -> restart full gate`

Owner-help:
`genuine cognition/authority blocker -> show exact sentence maps + failed evidence -> ask narrow question`.


## No failed-prose leakage in progress updates

Ordinary progress/status updates may report:
- current gate;
- whether a candidate failed;
- whether strategy changed;
- whether detector evidence is pending/green/red;
- whether owner help is required.

They must **not expose the failed candidate prose itself** before owner-delivery admission unless:
- Joel explicitly asks to inspect the failure; or
- Chat genuinely needs owner help, in which case use the sentence-map escalation packet above.

The owner must not become an involuntary intermediate reviewer through commentary.

## Exact-byte detector binding

A Pangram PASS applies only to:
- the exact submitted bytes;
- the exact detector/model/version;
- the exact paragraph/natural-boundary scope;
- the exact recorded text hash.

Any textual edit after Pangram, including punctuation or wording changes that alter the submitted bytes, invalidates that detector result for delivery admission and requires:
1. all materially affected internal gates to be re-run; and
2. Pangram to be run again on the new exact final bytes when the detector result remains part of admission.

Never transfer a Human result from a near-identical prior candidate to revised prose.

## Final owner-delivery receipt

When a candidate is finally shown to Joel, report only concise completion evidence:
- plain-reader comprehension: PASS;
- semantic/fidelity/preservation: PASS / zero unexplained substantive deltas;
- architecture/humanization reviews: PASS;
- Pangram: PASS on exact model-written boundaries, with exact result/model/version where available;
- any review that was genuinely unavailable, explicitly named rather than silently assumed.

Do not burden Joel with the internal failed-candidate history unless it materially explains a remaining tradeoff or he asks for it.
